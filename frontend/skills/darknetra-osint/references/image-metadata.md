# Image checks

Use this when imagery is relevant to a case question, including a request for image metadata. Run the check before writing conclusions about embedded information.

1. For an uploaded original, execute `node .agents/skills/darknetra-osint/scripts/osint.mjs metadata "<exact uploaded filename>"`. This reads bytes from this chat only, up to 32 MiB. It does not change the file. The SHA-256 identifies exactly the bytes examined. Camera images, PNGs, documents and other ExifTool-supported files may contain different tags; visual input does not substitute for this command.
2. For a supplied website review, inspect `page`'s `images` and `imageSummary` as well as its links. The inventory lists explicit image, lazy image, picture/srcset and social-preview references in the response; scripts are not executed. Listed images have not been retrieved. Select images relevant to the working question, avoiding decorative logos, tracking images, unrelated people and duplicates. Use an explicitly linked original where available; do not guess paths or infer an original from a thumbnail.
3. Execute `node .agents/skills/darknetra-osint/scripts/osint.mjs image-metadata "https://example.com/SYNTHETIC.png"` with the actual supplied/listed image URL. This reads one PNG, JPEG, GIF, WebP, TIFF, HEIC/HEIF or AVIF through the same public GET validation. Maximum 8 MiB, three redirects and normal source timeouts. Onion requests use Tor; run `tor-check` first. Do not use arbitrary download commands or bypass failures. At most five relevant remote images per turn shared with specialists; record pending images if more remain. These are assistant execution limits, not a whole-site collector.
4. Keep the helper JSON intact in one command result so the UI can record the source, retrieval time, SHA-256 and readable tags. `result`/`metadata.fields` contain bounded extracted tags and `text` explains them. `metadata.truncated` or extractor warnings mean an incomplete check. Remote image bytes are processed in memory and are **not archived**; the record identifies the retrieved response, not a preserved original. Do not claim evidentiary preservation. Ask for an authorised original upload when preservation or deeper review is needed.
5. Report exact useful tag names/values as source claims: camera make/model, embedded dates and timezone/offset when present, GPS, editing software and descriptive fields. Tags are editable and may describe digitisation or export rather than capture. Never silently assume a timezone or substitute the upload/server/retrieval timestamp. GPS alone does not establish where a person was or where a depicted event happened. Corroborate relevant claims against independent case sources; do not identify private people from appearance.
6. A successful check with no capture/GPS tags means those tags were not found in **this copy**; it does not prove tampering or deliberate stripping. State the usable details that remain, such as format/dimensions/hash. An unreadable file, unsupported response, limit or missing tool is a failed/unverified check, never proof of no metadata. Do not loop on the same failing bytes.
7. If original metadata matters, request the original camera/file export as a document, its custodian/source and the relevant time range. The current Telegram bot reader collects text/captions, not media bytes; it cannot inspect a photo from its caption. Use a supplied original attachment and accurately label the gap. Never claim a request was sent or a department contacted.

Implementation reference: [ExifTool stdin and piping documentation](https://exiftool.org/exiftool_pod.html#PIPING-EXAMPLES). This helper uses read-only stdin extraction with configuration loading disabled; it does not use any metadata-writing options.
