# Review decisions and records handoffs

Use these decisions when the source or transaction evidence actually raises the relevant question. They do not grant permission to access private accounts or identify a person from public technical identifiers.

| Trigger | Supported next step | What to record |
| --- | --- | --- |
| A supplied site links to another public page | The `site-review` queue follows same-origin references; deliberately inspect relevant external references separately. | Parent URL, actual destination, retrieved/failed/skipped/pending status and coverage limit. |
| A retrieved page contains a potentially relevant claim or offer | Read its context and ask the Evidence Reviewer to check the claim against original sources. | Exact URL, extracted-text line/section, short quotation, date/time, what was actually observed, corroboration and uncertainty. A keyword alone is not wrongdoing. |
| Login, registration, CAPTCHA or private content is encountered | Record the access gap and continue other accessible case sources. Request an existing authorized page export from its custodian if needed. | Exact public reference, which content remains unavailable, who can supply the export. No disposable accounts, logins, form submissions or bypasses. |
| A relevant wallet reference occurs | Confirm the network from the source. For Bitcoin, assign the Financial Analyst `wallet-review bitcoin <address> [1–25]`; review at most three relevant addresses per turn. | Source page and quote where the address appeared, exact address/network, API provenance, txids, inputs/outputs, satoshi and BTC amounts, UTC times, confirmations and history gaps. Never recursively expand into all counterparties. |
| The address/network is unsupported or unclear | Ask for the network and a case-scoped transaction export or public explorer reference. | Missing information; do not label a generic 0x address as a particular chain or claim an unsupported network was checked. |
| An ML assessment is relevant | Check `ml-schema`; run `ml-predict` only on a supplied training-compatible graph. Independently review the original transaction records as well. | Actual model output, input provenance, feature semantics, graph cutoff and model limitations. Raw wallet amounts do not produce the model's 102 opaque training features. The model/data team must supply a validated feature export; do not invent values. |
| A transaction counterparty is independently labelled as an exchange | Preserve the attribution source/date and confidence. Ask the case officer or financial-crime/records team to evaluate a focused request through the exchange's official legal/compliance process. | Network, txid, output index, address, asset/unit, amount, UTC time, attribution source and the narrow question. An exchange label can be stale or wrong; a shared transaction does not prove ownership. |
| Account/customer identity would help | Suggest an authorized, case-scoped preservation/records request to the identified custodian; do not send it automatically. | Needed account/deposit mapping and relevant customer records, legal basis/process for the responsible officer to assess, time range and a redacted export to bring back. Connecting a wallet does not reveal KYC, and no wallet connection, signature, transfer, seed phrase or private key is needed for this public review. |
| The user requests repeat monitoring | Use the app's actual schedule receipt and existing public-source review flow. | Check scope, schedule, last successful review, changes and failures. Do not claim a private site is monitored because its public login page was reachable. |

Exchange customer records are held by the provider, not published as an on-chain wallet field. FATF describes customer due diligence and record-keeping duties for virtual asset service providers; access to records depends on the holder and applicable official process. This reference is an unsent review handoff, not a legal determination. [FATF virtual assets overview](https://www.fatf-gafi.org/en/topics/virtual-assets.html).
