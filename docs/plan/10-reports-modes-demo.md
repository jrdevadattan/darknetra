# Plan 10 — Investigation pack, demo and offline modes, walkthrough, backup

Milestone M6 · Owners E (pack, walkthrough, backup), A (modes) · Depends on 07, 09.

**Goal.** A deterministic, hashed investigation pack whose every sentence traces to the store; demo mode that makes the stage run reproducible; offline mode that keeps the evidence lane alive; a scripted end-to-end walkthrough over HTTP that proves the backend without a UI; backup and restore that preserve hashes.

**Architecture.** `reports/model` builds a typed `ReportModel` from the store; `reports/narrative` asks the worker model for summaries under claim rules; `reports/render` produces Markdown and HTML from Jinja templates; the pack is stored through `ingest_bytes` as `REPORT` evidence with its own hash and a `reports` row. Modes are settings with explicit behaviours listed below.

## Report model

Sections, in order, each with `facts` (rows straight from the store) and an optional `narrative` (model text with verified claims):

1. **Cover**: case code, title, generated at, generated by, report version, SHA-256 of this document (filled after render by a second pass into the footer only), source classes present, `SYNTHETIC` banner when the case is a demo.
2. **Scope and authority**: scope notes, authority reference (redacted unless EXPORT), policy switches in force (Tor, person lookup, Telegram), limits.
3. **Executive summary** (narrative only; every sentence cites).
4. **Evidence inventory**: table of evidence code, kind, source class, origin, captured at, SHA-256, status, custody count; child evidence nested.
5. **Observations**: per type counts; tables for identifiers (wallets with chain and validity, fingerprints, contacts, locators) with evidence codes and spans.
6. **Link candidates and decisions**: each candidate with band, score, family list, feature table (name, value, weight, contribution, evidence codes, explanation), contradictions, decision (who, when, rationale), version history.
7. **Activity candidates**: label, score, features, evidence.
8. **Wallet assessments**: GNN result with threshold and caveat, sanctions with source, live summary evidence codes.
9. **Graph snapshot**: node/edge counts, confirmed relationships list (source, type, target, decision id); a `graph.json` attachment reference.
10. **Timeline**: case timeline entries in the report window.
11. **Monitoring**: watchlist items, runs summary, alerts with status and evidence codes.
12. **Findings**: PROMOTED findings with kind, claim, evidence, method and version.
13. **Methods and versions**: extractor bundle version, lexicon version, link config digest, activity config, trend config, embedding model, GNN model version, harness models used in threads.
14. **Limitations and contradictions**: unavailable lanes during the case, quarantined items, unverified claims dropped, contradictions found, the standing statement that scores are indicators, not proof.
15. **Evidence appendix**: for each cited evidence code: code, hash, captured at, source class, and the cited spans' text (redacted per role).

Options: `sections` subset, `redact: bool`, `include_appendix: bool`, `window: {from, to}`.

### Narrative rules

The worker model (`settings.worker_model`, or the offline model) receives the section's facts as JSON and returns prose plus a claims fence (plan 06 format). `claim_checker.verify` runs; unverified sentences are removed and listed under Limitations with the reason; the report still generates (scenario 36). No narrative is required for a valid pack: `narrative: false` produces facts-only sections.

### Redaction (by role of the generating actor, or `redact=true`)

Phones → `+91 98xxx xx210`; emails → `r***@domain`; onion locators and URLs → domain hash prefix `onion:9f3a…`; authority reference → `[withheld]`; images referenced by code only. Presidio (plan 16) plugs in at `redact.py` with the same interface.

### Rendering and storage

Markdown via Jinja templates with fixed ordering (tables sorted by evidence code, candidates by score desc then id); HTML via `markdown-it-py` with an inline print stylesheet (page breaks before sections, monospace for codes) so browsers export PDF; both stored through `ingest_bytes(source_class=REPORT, origin=REPORT)` giving the pack its own evidence code and SHA-256; `reports(version, storage keys, sha256, includes, claim_check, redaction)`. Regeneration creates version+1; nothing is overwritten.

### Endpoints

`POST /cases/{id}/reports {sections?, redact?, include_appendix?, narrative?}` → 202 with `report_id` and a job; `GET /reports`, `GET /reports/{rid}`, `GET /reports/{rid}/download?format=md|html` (EXPORT for unredacted; REPORT_GENERATE for redacted). Tool `build_investigation_pack {sections?, redact?}` (REPORTER, CASE_LEAD) returns `{report_id, evidence_code, sha256, unverified_dropped}`.

## Modes

### Demo mode (`settings.demo_mode`)

- Banner flag in `/admin/settings` and in every case with `demo=true`; the frontend shows `SYNTHETIC DEMO`.
- `monitor_interval_override = 120`.
- Replay cache active (plan 06); new successful runs are recorded into it.
- Seeding allowed with `--reset`; `scripts/seed_synthetic_case.py` refuses to run when `demo_mode=false` and the target DB has non-demo cases unless `--force`.
- Tor and person lookup switches on the demo case follow the case policy as seeded (person lookup on, Tor off).

### Offline mode (`settings.offline_mode`)

- Policy rule 1 denies every network tool with `NETWORK_REQUIRED`.
- Threads default to the offline harness; existing Claude threads continue only when the flag is off.
- `/health/ready` reports `harness: offline`; `/tools` lists network tools as `disabled_by_mode`.
- Embeddings: NullEmbedder allowed; search reports `dense_available=false`.
- `transcribe_image` uses Tesseract when installed, else `UNAVAILABLE`.

### Readiness fallbacks (automatic, logged, surfaced in `/health/ready`)

Claude CLI or key missing → offline harness for new runs; embedding model missing → lexical-only; Tor unreachable → dark fetch `UNAVAILABLE`; MCP gateway down → external tools omitted; scheduler failure → `degraded` and manual runs still work.

## Walkthrough (`scripts/demo_walkthrough.py`)

Runs the v2 demo flow over HTTP with SSE and prints a timed transcript; exits non-zero on any failure or unverified claim. Steps:

1. Login as `analyst.demo`; `--reset` seeds SYN-CHD-001 (plan 03) or reuses it.
2. Wait for processing; print evidence counts by source class.
3. Thread "Alias links": ask Q3 and Q4 from `evals/questions.yaml`; print steps and claims; assert `verification.ok`.
4. Decide: ACCEPT the planted candidate with a rationale; assert `/graph` has a CONFIRMED edge.
5. Thread "Wallet trail": ask Q6; assert GNN present (or explicit reason) and sanctions present.
6. Thread "Market presence": ask "Where else does KMK.Zirakpur appear publicly?"; with `--mock-osint` the adapters are stubbed; assert ≥ 1 `OSINT_SURFACE` capture cited.
7. Watchlists: add W1 and "safed line"; in demo mode wait up to 150 s for an alert; escalate it; assert a finding exists.
8. Report: generate with narrative; download Markdown; assert the appendix contains every cited code and `unverified_dropped == 0`.
9. Print a summary table (step, seconds, cost) and write `evals/out/walkthrough-<date>.json`.

CI runs the walkthrough with `--fake-harness --mock-osint` against the FakeHarness (plan 06) so the API surface is exercised on every merge.

## Backup and restore

- `scripts/backup.py --out backups/<ts>/`: `pg_dump -Fc` + `tar` of the vault + `manifest.json` listing every evidence code with its SHA-256 and byte size.
- `scripts/restore.py backups/<ts>/`: restore DB and vault into an empty target; then recompute hashes for every evidence row and fail on any mismatch (custody `VERIFIED` events written for the audit trail).
- Rehearse before the finale: backup → restore into a scratch DB → run the walkthrough with `--fake-harness`.
